# Test fixtures

**Status: convention only.** OpenMemory has no product code, so nothing reads these fixtures yet. This document fixes the convention now, while the fixture set is three files, so that Stage 1 inherits a checkable rule instead of inventing one per test.

## 1. Where fixtures live

Committed fixtures live under `tests/fixtures/`, one directory per subject:

| Directory | Holds |
|---|---|
| `tests/fixtures/events/` | Provider-neutral event envelopes, as described in [Architecture](ARCHITECTURE.md) under "Capture and normalized events". |
| `tests/fixtures/transcripts/` | Complete conversation turns — the unit an inline or standalone `/store` targets. |
| `tests/fixtures/repositories/` | Synthetic file, symbol, and language trees that *describe* a repository rather than containing one. |

Every file is named `<subject>.sample.json`: a lowercase, hyphenated subject, then `.sample.json`. The `.sample` segment marks the file as illustrative data with no live consumer, so a reader never mistakes it for a schema, a golden output, or captured production data.

A fixture with no identified consumer is speculative. Add one when a test needs it, not in anticipation of a test.

## 2. Determinism rules

A fixture's SHA-256 is recorded in [the manifest](../tests/fixtures/MANIFEST.md) and recomputed by a test, which is possible only because a fixture's bytes are identical on every machine and every run. Therefore a fixture:

- is JSON, with LF line endings, two-space indentation, and a single trailing newline;
- keeps its keys in a fixed, meaningful order — never re-sorted by a formatter, and never regenerated by a serializer whose key order is not guaranteed;
- contains no value that varies between machines or runs: no wall-clock time, no random or generated value, no host or user name, no absolute path, no environment-dependent separator;
- uses fixed literal identifiers typed into the file. `event_id`, `project_id`, and the other UUIDv7 identifiers of [Identifiers](IDENTIFIERS.md) §2 appear as literal UUIDv7-shaped strings. Never call `Guid.CreateVersion7()` — or any generator — to produce a fixture value;
- states time-valued and hash-valued fields as fixed literals too. They are illustrative shapes, not values recomputed from the payload; Stage 0 has no canonical serializer to recompute them with, and a recomputed value would change whenever that serializer did;
- is fictional content authored for this purpose. Never copy a real conversation, real repository content, real user data, or anything resembling a credential.

## 3. Line endings

`.gitattributes` pins `tests/fixtures/** text eol=lf`. The repository-wide `* text=auto eol=lf` already covers these files; the explicit rule exists so a future editor sees the dependency where the files are, because the checksums are taken over bytes and a CRLF checkout silently changes every one of them.

`.cs` files are the opposite — `.gitattributes` pins them to CRLF, and CI runs `dotnet format --verify-no-changes`, which fails on a mismatch. Keep the two straight: fixtures LF, C# CRLF. [SET-20260816-004](operations/setbacks/SET-20260816-004-readme-render-probe.md) is the recorded precedent for the general failure mode — a command that mixed two format expectations and produced a failure that looked like a content problem but was not.

## 4. Adding or changing a fixture

1. Add or edit the file under the right subject directory, following §2.
2. Regenerate the manifest table in [`tests/fixtures/MANIFEST.md`](../tests/fixtures/MANIFEST.md):

   ```bash
   cd tests/fixtures && find . -type f -name '*.json' | sort | while read -r f; do echo "$f  $(sha256sum "$f" | cut -d' ' -f1)"; done
   ```

   Never type a digest by hand.
3. Fill in the row's `Purpose` and `Consumed by` columns.
4. Commit the fixture and the manifest **together**. `FixtureManifestTests` fails when a fixture has no manifest row, when a row names a missing file, or when a digest disagrees — so a commit that changes one without the other does not build.

That coupling is the whole point of the manifest (`D-095`). A fixture quietly edited to make a failing test pass is indistinguishable in review from one edited to fix a real defect; requiring the digest to change in the same commit makes the first case a deliberate, visible act.

## 5. Secret-detection corpora are generated, never committed

**No secret-shaped string may be written into any file in this repository, fixtures included.** There is no exception for test data.

Secret-detection tests still need input, so their corpora are generated inside the test at run time from documented synthetic patterns, per `D-094` in the [decision register](DECISION_REGISTER.md). Two independent reasons:

- [Agent instructions](../AGENTS.md) prohibit writing a secret value into any file, including examples, placeholders, and templates.
- CI's `secret-scan` job runs gitleaks over the tree. A committed corpus would fail the build on exactly the content it exists to exercise — a self-inflicted failure with no upside.

The generation approach: assemble each candidate string at run time from documented components — a provider prefix constant, a separator, and a deterministic filler derived from a fixed seed or a fixed literal body string — inside the test method that consumes it. The assembled value never reaches disk, a log, a snapshot, an assertion message, or a model. It exists only in memory for the duration of the assertion. Because the components and the seed are fixed, the corpus is as deterministic as a committed file would be, without ever being one.

Do not "fix" the absence of a corpus file by committing one, and do not move a generated corpus into `tests/fixtures/` for convenience. If the generation rules need to change, change them here and in the test that reads them.
