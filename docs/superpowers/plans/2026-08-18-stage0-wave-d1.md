# Stage 0 Wave D1 — Threat Model Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Produce a repository-grounded threat model covering both the CI surface that exists today and the product architecture that exists as approved design, and SHA-pin the GitHub Actions.

**Architecture:** One document, `docs/security/openmemory-threat-model.md`, written in layers across several tasks. Foundation sections first (scope, assets, attackers), then the two evidence-separated parts, then a mandatory pause to confirm assumptions with the repository owner, then threats and mitigations — because threat ranking depends on assumptions and ranking before confirming them produces confident nonsense.

**Tech Stack:** Markdown, GitHub Actions, `gh` CLI, .NET 10 (for re-verifying an inherited test).

**Spec:** [docs/superpowers/specs/2026-08-18-stage0-wave-d1-design.md](../specs/2026-08-18-stage0-wave-d1-design.md)

## Global Constraints

Every task's requirements implicitly include this section.

- **No product behavior.** No `.cs` or `.ts` file gains logic. The Stage 0 exit gate's "no product capability is claimed" still binds.
- **Repository:** `June74/openmemory`. **Branch:** `codex/stage0-wave-d1`. Never commit to `main` — it is protected and will reject a direct push.
- **DCO required.** Every commit uses `git commit -s`.
- **Never write a secret value** into any file, including plausible-looking fake ones. The `secret-scan` job runs gitleaks over full history and will fail the build.
- **THE MARKING RULE, which is this wave's central discipline.** Every claim about the system is either evidenced by **code** (cite `path:line`) or by **approved design** (cite `ARCHITECTURE.md` or `DATA_AND_PRIVACY.md` by line, and mark it *designed, not implemented*). No sentence may describe an unbuilt control in the present tense as though it exists. Independent review has caught exactly this defect twice in this project already; in a threat model it is worse, because "we have a control for that" and "we designed a control for that" lead to opposite decisions.
- **Cite only decisions that exist.** Before citing any `D-0NN`, confirm it is in `docs/DECISION_REGISTER.md`. A citation to a non-existent decision reads authoritative and is worse than no citation.
- **Every branch push triggers CI**, and all six checks must pass. `main` is protected with administrator enforcement.
- **Use Bash** (Git Bash available), never a PowerShell pipeline. For long Markdown, prefer writing files with a heredoc using a quoted delimiter, or a file-writing tool — unquoted heredocs mangle backticks and `$`.

Per D1-7 and spec §4.1. Four sub-areas:

### Task 6: SHA-pin the GitHub Actions

**Files:**
- Modify: `.github/workflows/ci.yml`

**Interfaces:**
- Consumes: Part A's supply-chain analysis.
- Produces: immutable action references.

- [ ] **Step 1: Resolve each tag to its commit SHA**

```bash
cd "C:/Users/2006i/projects/openmemory"
for ref in $(grep -oE 'uses: [^ ]+' .github/workflows/ci.yml | sed 's/uses: //' | sort -u); do
  repo="${ref%@*}"; tag="${ref##*@}"
  sha=$(gh api "repos/$repo/git/ref/tags/$tag" --jq '.object.sha' 2>/dev/null)
  # annotated tags point at a tag object; dereference to the commit
  type=$(gh api "repos/$repo/git/ref/tags/$tag" --jq '.object.type' 2>/dev/null)
  if [ "$type" = "tag" ]; then sha=$(gh api "repos/$repo/git/tags/$sha" --jq '.object.sha'); fi
  echo "$ref -> $sha"
done
```

**The annotated-tag dereference matters.** A tag can point at a tag object rather than directly at a commit. Pinning the tag object's SHA is not the same as pinning the commit, and the workflow would fail to resolve it.

- [ ] **Step 2: Rewrite each `uses:` line**

Format — the version comment is not decoration:

```yaml
uses: actions/checkout@<40-char-sha>  # v7.0.1
```

**Dependabot reads that trailing comment** to know which version a SHA represents, and uses it to offer updates. Omit it and you have pinned the action *and* blinded the mechanism that keeps the pin current — trading a staleness problem for a quieter one.

- [ ] **Step 3: Verify the pins are real SHAs**

```bash
cd "C:/Users/2006i/projects/openmemory"
echo "=== every uses: is a 40-char SHA with a version comment ==="
grep -nE 'uses: ' .github/workflows/ci.yml | while read -r line; do
  echo "$line" | grep -qE '@[0-9a-f]{40}\s+#\s*v?[0-9]' && echo "OK   $line" || echo "NOT PINNED: $line"
done
echo "=== no mutable tag refs remain ==="
grep -nE 'uses: [^ ]+@v[0-9]+\s*$' .github/workflows/ci.yml && echo "FAIL: mutable tag remains" || echo "PASS"
```

Expected: every line `OK`, and `PASS`.

- [ ] **Step 4: Push and confirm CI still passes**

The pins are only correct if the workflow still resolves and runs. Push, wait for the run, and confirm all six jobs pass. A wrong SHA fails at action-resolution time with an unhelpful message, so a green run is the proof.

- [ ] **Step 5: Confirm Dependabot still recognises the pinned form**

```bash
cd "C:/Users/2006i/projects/openmemory" && cat .github/dependabot.yml
```

Confirm the `github-actions` ecosystem entry is intact. Dependabot's own behaviour is observable only on its schedule, so record that this is a configuration check plus a documented expectation — not proof — and say so rather than overclaiming.

- [ ] **Step 6: Commit**

```bash

git commit -s -m "Pin GitHub Actions to commit SHAs

A tag can be moved by its author to point at different code; a commit
SHA cannot. Each pin keeps a trailing version comment so Dependabot
```
